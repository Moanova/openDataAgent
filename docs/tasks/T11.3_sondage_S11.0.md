### `last_modified` vs `last_update` en v2 (constat crucial)
Sur le jeu étalon (résultats définitifs 1er tour 2022, Ministère de l'Intérieur) :
- `last_modified` = 2022-04-19 (dernière modification des métadonnées)
- `last_update` = 2022-04-14 (dernière mise à jour d'une ressource)

**Décision de mapping** : `derniere_maj` doit être alimenté depuis **`last_update`** en v2 (sémantique la plus proche de l'usage projet : fraîcheur des données, fenêtre de mise à jour). C'est aussi le champ support du tri `-last_update`. À confirmer par le concepteur.

### Tri
| Tri normalisé | v1 (`sort`) | v2 (`sort`) |
|---|---|---|
| `pertinence` | absent (défaut v1) | absent — **le tri implicite de la v2 est la pertinence** (moteur du site) |
| `recent` | `-last_update` | `-last_update` ✅ |
| `vues` | `-views` | `-views` ✅ |
| `reutilisations` | `-reuses` | `-reuses` ✅ |

Autres tris v2 OK : `created`, `-created`, `last_update`, `-followers`, `-views`. Non supportés (400) : `title`, `-last_modified`, `-datasets`.

### Fenêtre de mise à jour
- v1 : paramètre `last_update_range` (valeurs `last_month`, `last_year`...).
- v2 : **`last_update_range` rejeté (HTTP 400)**. Aucun équivalent direct testé ne fonctionne.
- Facette `last_update` présente dans la réponse (facettes de dates), suggérant un filtrage par dates — mais pas de paramètre simple équivalent.

**Décision requise (concepteur)** : soit (a) implémenter la fenêtre côté client (filtrage des résultats sur `last_update` après réception — dégrade la pertinence du `total`), soit (b) déprécier le paramètre `fenetre_maj` de `rechercher_jeux` (évolution de contrat v1.2.0 → v1.3.0), soit (c) documenter un comportement « toutes » constant pour data.gouv.fr v2.

### Pagination
- `page` + `page_size` identiques ; `page_size=101` accepté (non plafonné à 100 comme en v1 ?) — à vérifier : v1 plafonnait `page_size` à 100.
- Page au-delà du total → **HTTP 400** (v1 : 200 avec liste vide). À gérer : la pagination conduite par le code doit s'arrêter sur 400 ou sur `next_page` absent (préférable : `next_page`).
- `next_page` absent sur dernière page — l'extraction du numéro de page est inchangée.

### Inventaire (`lister_ressources_api`) — impact majeur
- v1 : `GET /api/1/datasets/{id}/` → `resources` liste embarquée.
- v2 : `GET /api/2/datasets/{id}/` → `resources` = subsection `{rel, href, total}`. Il faut un **second appel** : `GET /api/2/datasets/{id}/resources/?page=&page_size=` → enveloppe paginée (`data`, `total`, `page`, `page_size`, `next_page`, `previous_page`).
- Champs ressource : `id`, `title`, `description`, `url` (lien direct), `format`, `mime`, `filesize`, `checksum` (sha1), `type` (`main`/secondary), `filetype`, `created_at`, `last_modified`, `latest`, `metrics.views`, `extras` (`check:available`, `check:status`...), `schema`, `preview_url`, `harvest`, `geopf`.
- **Atout** : `extras.check:available` / `check:status` permettent un contrôle de disponibilité gratuit — candidat pour fiabiliser `telecharger_brut`/`extraire_ressource` (hors périmètre T11.3, à noter pour T7.1).
- 404 détail jeu : comportement identique (statut `jeu_introuvable`).

### API tabulaire (hors périmètre — vérification demandée)
- `https://tabular-api.data.gouv.fr/api/resources/{rid}/` : **200 sur ressource CSV indexée** (vérifié sur `ecde8958-7232-4e9d-be53-531b6f83ebe1`), 404 sur ressource non indexée.
- `/data/` : enveloppe `{data, links, meta}` inchangée.
- **Conclusion : `est_indexee_api_tabulaire`, `interroger_ressource_api` et `profil_ressource_api` sont à conserver tels quels** (base URL tabulaire distincte, non impactée par la bascule v2).

### Organisations (préparation T11.2)
- `GET /api/2/organizations/search/?q=` : même enveloppe paginée, items avec `id`, `name`, `slug`, `badges` (`public-service`, `certified`), `metrics.datasets`. Équivalent v2 direct de l'endpoint v1 envisagé — T11.2 pourra s'appuyer sur la v2 d'emblée.

### Filtres éprouvés en v2 (recherche)
- `license=fr-lo` ✅, `organization={id}` ✅ (utile T11.2), `tag=` ✅, `topic=` ✅, `geozone=` ✅, `format_family=tabular` ✅, `discontinued=false` ✅, `archived=false` ✅.

## Points à trancher par le concepteur avant implémentation
1. **Mapping `derniere_maj`** : `last_update` (recommandé) vs `last_modified`.
2. **Fenêtre de mise à jour** : dépréciation du paramètre (recommandé — b), filtrage client, ou fenêtre constante « toutes ».
3. **Pagination 400** : s'arrêter sur `next_page` absent (recommandé), sans dépendre du 400.
4. **Inventaire** : second appel vers la subsection `resources` — plafond `page_size` pour absorber les jeux à beaucoup de ressources (le href par défaut propose `page_size=50` ; les jeux à >50 ressources nécessiteront la pagination — itérer sur `next_page`).

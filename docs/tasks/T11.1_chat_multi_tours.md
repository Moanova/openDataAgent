## Architecture

```
┌─────────────┐     ┌──────────────────────────────────────────────┐
│  src/main.py │     │           src/agent/boucle.py                 │
│  chat (REPL) │────▶│  ConversationServeur                          │
│  stop / EOF  │     │  - creer_conversation(agent, id, plafond)     │
└─────────────┘     │  - tour_conversation(conv, message)           │
                    │    └─ _envoyer : start_stream (tour 1)       │
                    │    └─ _envoyer : append_stream (tours 2+)    │
                    │    └─ boucle tool-calling côté client         │
                    │  - cloturer_conversation(conv)                │
                    │    └─ journal fin + conversations.delete      │
                    └──────────────────────────────────────────────┘
                              │
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
    ┌─────────────────┐ ┌────────────┐ ┌─────────────────────┐
    │ client.beta.    │ │ executer_  │ │ JournalConversation │
    │ conversations   │ │ outil (5   │ │ (schéma multi-tours)│
    │ start_stream    │ │ outils)    │ │                     │
    │ append_stream   │ │            │ │                     │
    │ delete          │ │            │ │                     │
    └─────────────────┘ └────────────┘ └─────────────────────────┘
```

Flux d'un tour :
1. `tour_conversation` envoie le message utilisateur (`start_stream` au tour 1, `append_stream` ensuite).
2. Le serveur répond par un stream d'événements SSE : `message.output.delta` (texte), `function.call.delta` (tool_calls).
3. Chaque tool_call est exécuté **localement** (`executer_outil` → fonction cœur), jamais par l'API.
4. Les résultats sont renvoyés au serveur par `append_stream` (entrées `function.result`).
5. Itération jusqu'à la réponse finale (pas de tool_call) ou au plafond du tour.

## Schéma du journal multi-tours

```
contexte          (une fois)  id_execution, modèle, empreinte du prompt (sha256 tronquée), plafond, date
debut_tour        (par tour)  numero_tour, contenu (message utilisateur)
raisonnement_agent            tour (invocation dans le tour), numero_tour, contenu
outil_invoque                 outil, arguments, tour, numero_tour
outil_resultat                outil, statut, tour, numero_tour, message
plafond_atteint               numero_tour, nb_invocations, plafond
erreur_api                    numero_tour, detail, nb_invocations
fin_tour          (par tour)  numero_tour, statut, nb_invocations, synthese, plafond
fin               (une fois)  statut, nb_tours, nb_invocations
```

Les événements `message_utilisateur` et `reponse_finale` de l'ancienne boucle one-shot sont supprimés. Le rejeu `extraire_invocations` (base TA-01/TA-02) est inchangé.

## Évolutions futures consignées

- **Plafond global de sécurité** (ex. 50 invocations/conversation) si des conversations longues se généralisent.
- **Étape A0** : question de clarification avant recherche si la demande est ambiguë.
- **Conservation du contexte côté client** (option (a) du kanban) reste une alternative si le coût serveur ou la dépendance à `beta.conversations` devenait problématique — l'isolation du contact API dans `boucle.py` rend la migration peu coûteuse.

## Points de vigilance pour la validation réelle (E8)

1. **Premier tour** : `start_stream` crée la conversation — vérifier que le `conversation_id` est bien lu sur l'événement `conversation.response.started`.
2. **Boucle tool-calling** : les `function.call.delta` arrivent **par fragments regroupés par `output_index`** (un appel = N deltas) — vérifier la reconstitution (identité sur le 1er delta, arguments concaténés). **Corrigé en E8a** (1er test réel du 20/10 : erreur 400 « Duplicate function results » causée par un delta traité comme un appel complet) ; à re-vérifier en réel.
3. **Suppression** : `conversations.delete` en fin de flux — vérifier l'idempotence (404 = succès).
4. **Prompt** : vérifier que l'agent propose bien (A4) sans acquØrir spontanØment, et acquiert sur validation explicite.
5. **Journal** : vérifier le schéma multi-tours sur un fichier réel `conversations/<id>/conversation.jsonl`.
6. **Manifeste T10.8** : l'acquisition validée au tour N doit produire une entrée dans `data/raw/<id>/manifeste_acquisitions.json`.

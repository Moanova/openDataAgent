## Contexte et motivation

Trois familles de traces s'accumulaient sans limite par `id_execution` (`AAAAMMJJ_HHMMSS_<hash6>`) : `data/raw/<id>/` (fichiers acquis + manifeste T10.8), `data/executions/<id>/` (inventaire persistant T10.2), `conversations/<id>/` (journal T11.1) — plus les logs `logs/openDataAgent_<id>.log` (fichiers plats). `docs/specs/stockage.md` §6 mentionnait ce besoin en « améliorations futures ».

## Décisions actées (22/10/2026)

1. **Critère** : âge lu dans le préfixe date de l'`id_execution` ; défaut **30 jours**, paramétrable (`--age-jours`).
2. **Protection** : l'exécution courante est **toujours protégée**, même ancienne. Fail-safe : tout nom non reconnu (ou date invalide) est **conservé** — on ne supprime que ce qu'on reconnaît.
3. **Commande dédiée** `nettoyer` (pas un outil agent : pas de contrat JSON, pas de bump de version).
4. **Hook auto** désactivé par défaut, activé par `NETTOYAGE_AUTO=1` (pas de suppression de données sans consentement explicite) ; `nettoyer` exclu du hook.
5. **Périmètre** : 4 racines, dont `logs/` traité par pattern de nommage (`openDataAgent_<id>.log`), les registres globaux (`data/registry.json`, `data/registre_acceptations.json`) exclus.

## Hors périmètre

- Pas d'outil agent (le nettoyage n'est pas une capacité du chat).
- Aucune évolution de contrat (aucun schéma modifié, aucune version bumpée).
- `data/processed/` n'existe pas encore (partie 2) — à ajouter si le répertoire apparaît.

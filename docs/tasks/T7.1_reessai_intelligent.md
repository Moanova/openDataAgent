## Contexte et motivation

Le projet a déjà un mécanisme de reprise **basique et synchrone** dans `src/utils/http.py` :

| Mécanisme | Où | Détail |
|---|---|---|
| Reprise sur statuts transitoires | `appel_api` (`http.py:104`) | 429, 502, 503 → 3 tentatives, délais **fixes** `(1, 2)` s (`DELAIS_TENTATIVES`, `http.py:39`) |
| Reprise sur erreur réseau | `appel_api` (`http.py:96`) | `RequestException` (timeout, DNS, connexion) → idem |
| Reprise téléchargement | `telecharger_fichier` (`http.py:360`) | 3 tentatives, mêmes délais fixes |
| **Aucun retry** | `http.py:118` | Tout statut ≥ 400 hors transitoires → `echec_technique` immédiat (y compris 403, 410, 400 — retry inutile) |

**Trous constatés** (analyse du 22/10/2026, SESSIONS.md) :

1. **Délai fixe** : un 429 avec en-tête `Retry-After` n'est pas respecté ; pas de backoff exponentiel ni de jitter (risque thundering herd).
2. **Coupure mid-stream non rattrapée** : dans `telecharger_fichier`, si `iter_content` lève (`ChunkedEncodingError`) **après** le début du flux, l'exception n'est pas convertie en `ResultatAppel` — le `.part` reste orphelin et l'appel ne produit pas de retour structuré propre. Bug latent.
3. **Pas de reprise à l'octet** : un `.part` existant est écrasé, pas repris (header `Range`) — coûteux sur les gros fichiers (ex. ZIP 34,7 Mo).
4. **4xx définitifs traités comme transitoires** : 403/410/400返却 `echec_technique` sans distinction — le retry y est inutile, et le registre les consigne comme `serveur_origine_bloque` sans nuance.
5. **Registre : tout échec est définitif** — un 503 de 2 minutes fige la source comme inaccessible pour la session (`download.py:88`, `registry.py:90`), alors qu'un réessai différé aurait pu réussir.

## Hors périmètre (acté 22/10/2026)

- **Circuit breaker agentique** (ne pas solliciter un serveur d'origine après N échecs consécutifs dans une session, pour préserver le plafond d'invocations) → **T7.7**, logique de boucle/prompt A4, pas client HTTP.
- **Réessai inter-tours piloté par l'utilisateur** (l'utilisateur dit « réessaie » au tour suivant) → évolution du prompt A4, hors T7.1.

## Plan d'implémentation (E0..E7)

### E0 — Fondations (constantes et helpers)
- `src/utils/http.py` : constantes `DELAI_BASE_MS`, `DELAI_PLAFOND_MS`, `JITTER_MAX_MS`, `NB_TENTATIVES_DEFAUT = 3`, `STATUTS_TRANSITOIRES = {429, 502, 503, 504}`, `STATUTS_DEFINITIFS_SANS_RETRY = {400, 401, 403, 404, 410}` (404 déjà traité à part).
- Helper `_delai_retry(tentative, retry_after: Optional[float]) -> float` : `min(DELAI_PLAFOND_MS, DELAI_BASE_MS * 2**(tentative-1)) + jitter`, plafonné par `Retry-After` si fourni.

### E1 — Backoff exponentiel + jitter + `Retry-After`
- `appel_api` et `telecharger_fichier` : remplacer `DELAIS_TENTATIVES` fixe par `_delai_retry`.
- Lire `Retry-After` (secondes ou date HTTP) sur 429/503 ; le respecter comme borne supérieure du délai.
- **Tests** : TU-81 (429 avec `Retry-After: 5` → délai respecté, mock `time.sleep`), TU-82 (backoff croissant 1s→2s→4s avec jitter borné).

### E2 — Distinction transitoires/définitifs
- `appel_api` : si statut dans `STATUTS_DEFINITIFS_SANS_RETRY` → retour immédiat `echec_technique`, **sans** retry, avec `donnees.motif = "definitif"` (403 → `acces_refuse`, 410 → `ressource_supprimee`, 400 → `requete_invalide`).
- Le 404 garde son traitement spécifique (`statut_404` paramétrable, inchangé).
- **Tests** : TU-83 (403 → 1 seul appel, `motif=definitif`), TU-84 (410 → idem), TU-85 (400 → idem).

### E3 — Reprise `Range` sur `.part` + rattrapage mid-stream
- `telecharger_fichier` :
  - Si `<destination>.part` existe au début → envoyer `Range: bytes=<taille_part>-` ; en 206, reprendre l'écriture en `ab` ; en 200 (serveur ignore Range), repartir de zéro en `wb`.
  - Attraper `requests.exceptions.ChunkedEncodingError` (et `ConnectionError` mid-stream) **dans** la boucle `iter_content` → traiter comme échec transitoire (retry), le `.part` est conservé pour la reprise.
  - Ne jamais laisser de `.part` orphelin en cas d'échec définitif : le supprimer (sauf si reprise possible ultérieirement — décision : conserver le `.part` uniquement si statut transitoire, supprimer sinon).
- **Tests** : TU-86 (`.part` existant + 206 → reprise à l'octet, contenu final complet), TU-87 (coupure mid-stream simulée → retry, `.part` conservé, succès au 2e essai), TU-88 (`.part` + 200 → écrasement propre), TU-89 (échec définitif → `.part` supprimé, pas de fichier final).

### E4 — `nb_tentatives` dans les contrats (évolution additive)
- `ResultatAppel` : nouveau champ `nb_tentatives: int = 1`.
- Propagé dans `donnees.nb_tentatives` des réponses cœur (`search.py`, `download.py`, `extraction.py`, `query.py`) en cas d'échec (et succès après retry).
- **Contrats** : `contrats/manifeste.json` → `rechercher_jeux` 1.3.0 → **1.4.0**, `telecharger_brut` 1.1.0 → **1.2.0**, `extraire_ressource` 1.1.0 → **1.2.0**, `interroger_ressource` 1.1.0 → **1.2.0** (champ additif `nb_tentatives` dans `donnees` en sortie) ; miroirs Pydantic (`src/contracts/*.py`) et schémas jsonschema (`contrats/schemas_api/*.reponse.json`) mis à jour ; `valider_coherence_contrat` doit rester vert.
- **Tests** : TU-90 (succès au 1er essai → `nb_tentatives=1`), TC (cohérence contrat mise à jour).

### E5 — Marquage registre « à retenter » vs « définitif »
- `src/utils/registry.py` : `consigner_echec_technique` accepte un paramètre `reproductible: bool` (ou `statut_reprise: "a_retenter" | "definitif"`).
  - Transitoire épuisé (429/502/503/504/réseau après 3 tentatives) → `statut_reprise: "a_retenter"`.
  - Définitif (403/410/400) → `statut_reprise: "definitif"`.
- Invariant registre : aucune entrée supprimée/modifiée — le champ est additif, les entrées existantes (sans le champ) restent valides (défaut `definitif` en lecture).
- `rapport_pour_agent()` : expose le champ pour que le prompt A4 puisse distinguer.
- **Tests** : TU-91 (transitoire → `a_retenter`), TU-92 (définitif → `definitif`), TU-93 (rétrocompatibilité lecture entrée sans champ).

## Décisions de conception actées (22/10/2026)

1. **Périmètre T7.1 = client HTTP uniquement.** Le circuit breaker agentique est séparé en T7.7 (boucle/prompt, pas HTTP).
2. **Backoff exponentiel + jitter**, plafonné, avec respect de `Retry-After` — remplace les délais fixes `(1, 2)` s.
3. **Les 4xx définitifs (400, 401, 403, 410) ne sont jamais retentés** — retour immédiat avec `motif` explicite. Le 404 garde son traitement à part (inchangé).
4. **Reprise `Range` sur `.part`** : un `.part` existant est repris (206) ou écrasé (200). Une coupure mid-stream est un échec transitoire (retry, `.part` conservé). Un échec définitif supprime le `.part`.
5. **`nb_tentatives` est additif** dans les contrats (pas de rupture) : bump de version mineure des 4 outils concernés.
6. **Registre : champ additif `statut_reprise`** (`a_retenter` | `definitif`) ; rétrocompatible en lecture (défaut `definitif`).
